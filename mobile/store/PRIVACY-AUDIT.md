# Privacy audit — Eventsli Check-in, 2026-11-14

Sixteen questions, answered from the code and the generated native projects.
"Fixed" means changed in the working tree and covered by a test
(`test/privacy.test.ts`, `test/release.test.tsx`), not committed or
released. Nothing in production was touched; the privacy policy is not
published.

| # | Question | Finding | Status |
|---|---|---|---|
| P-01 | Sentry installation id | Sentry's native layer sets `user.id` to a per-install id when no user is set (`node_modules/@sentry/react-native/ios/RNSentry.mm`, `fetchNativeDeviceContexts`), and native crash events and session pings are sent from native code without passing the app's scrubber. | **Fixed:** `enableNative: false`, `enableAutoSessionTracking: false` (`src/lib/monitoring.ts`). No Sentry install id or session is sent. Cost: native-code crashes are not reported. Sentry is off anyway until a DSN is built in. |
| P-02 | Apple classification | Missing: **Device ID** (Expo update id, see P-03) and **Search History** (Find Guest). Crash and performance data are correctly "not linked"; email, name and check-ins correctly "linked". | **Fixed** in `PRIVACY.md` and `ios.privacyManifests`. |
| P-03 | Google Data safety | **Undeclared third party:** `expo-updates` sends a persistent random `EAS-Client-ID` to u.expo.dev on every start (`expo-updates/ios/EXUpdates/AppLoader/FileDownloader.swift:464`, Android `FileDownloader.kt:900`). "No sharing" is right only if Expo and Sentry are processors under a DPA. | **Fixed** declarations (Device or other IDs; in-app search history). **Owner:** confirm DPAs with Expo and Sentry. |
| P-04 | Sentry leakage | **Leak:** Sentry's fetch spans carry the full `url` and `http.query` (`@sentry/core/build/cjs/fetch.js:198-214`); the scrubber did not touch `spans` or `transaction`, nor drop `http.query`, so a guest search (`?q=Sara`) would reach Sentry in sampled scans. Ids (UUIDs) were not scrubbed. Tokens, emails, users, console output were already handled. | **Fixed:** URL query strings removed from all text, UUIDs → `[id]`, spans and transaction names scrubbed, `http.query`/`body`/`params`/`seat`/`search` dropped. Tests P-04. |
| P-05 | Offline database encryption | SQLCipher via `useSQLCipher`, raw 256-bit key in the Keychain/Keystore (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`), WAL encrypted by SQLCipher. Gaps: `PRAGMA key` is silently ignored on plain SQLite, so a build without SQLCipher would store guest data in clear without any sign; deleted rows stayed in free pages; temp files could go to disk. | **Fixed** (`src/lib/dbSecurity.ts`): a store build refuses an unencrypted database (`PRAGMA cipher_version`), `secure_delete = ON`, `temp_store = MEMORY`. **Check on device:** first TestFlight/internal build must scan normally (it would fail loudly if SQLCipher were missing). |
| P-06 | Guest data deletion | Verified in code (`offlineList.ts`, `session.ts`): deleted on leaving the event, sign-out, a 401 (door closed), offline mode off, organizer switching offline check-in off (403), and on any load or pull more than 24 h after the event. Limit: the 24 h rule runs when the app opens; a phone never opened again keeps the (encrypted) copy. | Verified. Limit documented in the policy draft. |
| P-07 | Check-in retention | **Bug:** the 48 h / 2,000 rule ran only for the event being opened (`scanLog.load`), so other events' logs, with guest answers, stayed for good. Settled rows also kept the ticket's QR code (a bearer pass). Server side: the `scans` table is **never purged** (no job, no policy). | **Fixed** on the phone: `prune()` covers every event; settled rows keep no QR (`storedQr`). Pending scans are kept until uploaded (they are admissions). **Owner:** decide server retention for `scans`. |
| P-08 | After sign-out | Tokens deleted from the Keychain; guest list wiped. **Gap:** the in-memory query cache (guest lists, searches) and scan log were not cleared. Pending (not yet uploaded) scans stay, encrypted, until uploaded by the next person working that event, or kept. | **Fixed:** `queryClient.clear()` and the scan log cleared on leaving a door and on sign-out. Pending scans: by design (no admission lost). |
| P-09 | 24 h vs 14 days | Website: "at most 24 hours". App sessions: 14 days (`backend/services/sessionService.js:22`). | **Open (owner/legal):** policy wording drafted in `PRIVACY.md`. |
| P-10 | Privacy manifest | Now declares: email, name, other user content, search history (linked); device id, crash, performance (not linked); no tracking; required-reason APIs aggregated from the bundled SDKs. Verified with `expo config --type introspect`. | **Fixed.** Re-check the generated `PrivacyInfo.xcprivacy` in the first iOS build (cannot be generated on Windows). |
| P-11 | Android permissions | Generated with `expo prebuild` and checked against every library manifest. **Found:** `READ_MEDIA_IMAGES` (expo-screen-capture; a Play policy rejection risk) and `SYSTEM_ALERT_WINDOW` (Expo template). No location, no microphone (already removed). `DETECT_SCREEN_CAPTURE` must stay: removing it crashes Android 14+ at start. | **Fixed:** blocked `READ_MEDIA_IMAGES/VIDEO/AUDIO`, `SYSTEM_ALERT_WINDOW`. Final set: CAMERA, INTERNET, ACCESS_NETWORK_STATE, VIBRATE, MODIFY_AUDIO_SETTINGS, DETECT_SCREEN_CAPTURE. Confirm in the merged manifest of the first EAS build (no Android SDK here). |
| P-12 | Android backup | `allowBackup="false"`; device transfer limited to shared preferences minus SecureStore (`expo-secure-store` `data_extraction_rules`). Database, tokens, keys never leave. iOS: keys are this-device-only, the database is unreadable elsewhere. | Verified. |
| P-13 | Account deletion | No code deletes an account (no route, no job); the policy says "until you ask us to close it". App: a deleted account's sessions stop working (401), and the app then wipes its local data. Apple 5.1.1(v) does not require in-app deletion (the app creates no accounts). | **Open (owner):** write the manual deletion runbook (users, sessions, door devices, scans to anonymise or keep). |
| P-14 | Privacy policy vs app | Five differences: no app section; 24 h vs 14 days; Expo and Sentry missing; no check-in retention; deletion process. | **Open (owner/legal):** draft text in `PRIVACY.md`. Not published. |
| P-15 | Network | Store builds: HTTPS only (client refuses non-HTTPS, `NSAllowsArbitraryLoads` false, Android cleartext only in the debug manifest). **Note:** the guest search is sent in the URL (`?q=`), so names land in server/nginx access logs ("deleted after a short period"). Device name minimised: the app now sends the phone model, not its personal name. | Fixed (HTTPS, device name). **Owner:** confirm the access-log retention, or strip `q` from nginx logs. |
| P-16 | Offline sync | Idempotent by `clientScanId`; a lost answer is held, not dropped; `error` answers retried up to 5 times, then settled with the error shown; pending rows are never pruned; uploads are serialised (single `syncing` guard). After the fixes, settled rows keep no QR. Not lost: held scans survive sign-out. Exposure: held scans keep their QR (needed to upload) inside the encrypted database. | Verified; covered by `test/scanLog.test.ts`, `test/offline.test.ts`. |

## Individual developer accounts (owner, 2026-11-14)

- **Apple (individual):** the App Store shows the owner's **personal legal
  name** as the seller, not "Eventsli". The privacy policy names who is
  responsible for the data; make sure it matches the seller (or move to an
  organization account later — an app can be transferred). In the EU, if the
  owner declares **trader** status under the DSA, the address, phone and email
  entered become public on the EU storefronts.
- **Google Play (personal account created after Nov 2023):** a **closed test
  with at least 12 testers opted in for 14 continuous days** is required
  before production access can even be requested. Plan the door-team pilot as
  that closed test. The developer name and contact email are public.
